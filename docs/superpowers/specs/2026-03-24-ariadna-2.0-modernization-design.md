# Ariadna 2.0 Modernization Design

## Summary

Comprehensive modernization of Ariadna to align with Claude 4.6 platform capabilities: Memory Tool patterns, Agent Skills system, and updated prompting best practices. Clean break (2.0) using a vertical slice strategy — modernize the core plan/execute/verify loop end-to-end first, then apply patterns to the rest.

## Context

Ariadna is a meta-prompting and context engineering system for building Rails applications with Claude Code. The current 1.x architecture was designed for earlier Claude models and uses:

- 119 data files (~31,400 lines of prompts) with verbose, step-by-step execution protocols
- A monolithic STATE.md for cross-session persistence
- 14 specialized agents (~8,200 lines) with detailed instruction sets
- 30 workflow files (~9,300 lines) prescribing exact orchestration sequences
- 34 templates (~8,800 lines) including codebase and research subdirectories
- Domain-specific executor agents (backend, frontend, testing) for Rails knowledge

Three new Claude platform capabilities necessitate updates:

1. **Memory Tool** — First-class API primitive for persistent file-based memory with view/create/str_replace/insert/delete commands
2. **Agent Skills** — Structured SKILL.md packaging with YAML frontmatter and progressive disclosure (3 levels of loading)
3. **Claude 4.6 prompting changes** — Adaptive thinking, native parallel tool calling, native subagent orchestration, overeagerness on aggressive prompting, context awareness

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Compatibility | Clean break (2.0) | Freedom to rethink architecture without legacy constraints |
| Skills model | Hybrid | Core orchestration stays as commands; Rails domain knowledge becomes standalone Skills |
| Memory | Adopt Memory Tool patterns | Align with Anthropic's recommended persistence; granular files over monolith |
| Prompt trimming | Significant | Trust 4.6 for the "how"; focus prompts on goals, constraints, success criteria |
| Domain focus | Rails-only | Clear identity, focused value proposition |
| Model targeting | Generic (opus/sonnet/haiku) | Let Claude Code resolve to latest versions |
| Implementation | Vertical slice | Prove architecture on core loop before applying everywhere |

## Architecture

### Layer Diagram

```
┌─────────────────────────────────────────────┐
│  Commands (slash commands)                   │
│  Same user interface, simplified internals   │
├─────────────────────────────────────────────┤
│  Workflows (orchestration)                   │
│  Goal + constraints + success criteria       │
│  Trust 4.6 for execution strategy            │
├─────────────────────────────────────────────┤
│  Agents (lean subagents)                     │
│  Role + goal + boundaries + output format    │
│  No step-by-step protocols                   │
├──────────────────────┬──────────────────────┤
│  Skills (portable)   │  State (Memory Tool) │
│  Rails backend       │  view/create/replace │
│  Rails frontend      │  File-based memory   │
│  Rails testing       │  Progress tracking   │
│  Security            │  Cross-session       │
│  Performance         │  continuity          │
└──────────────────────┴──────────────────────┘
```

### Key Architectural Changes from 1.x

1. **Workflows shrink dramatically** — Describe goal, constraints, and success criteria. Claude 4.6 decides how to orchestrate.
2. **Agents become goal-oriented** — ~50-80 lines (role, goal, boundaries, output format) vs current ~300-line protocols.
3. **Rails knowledge becomes Skills** — Proper SKILL.md packages with progressive disclosure. Usable independently of Ariadna.
4. **STATE.md replaced by Memory directory** — Granular files following Memory Tool patterns. Agents read only what they need.
5. **Init tool returns paths, not contents** — Agents self-manage context loading, aligned with 4.6's capabilities.

## Memory/State System

### Current (1.x)

Single `.ariadna_planning/STATE.md` (~100 lines) with sections for position, metrics, decisions, blockers. Updated via `ariadna-tools state` subcommands with field-specific methods (`advance-plan`, `record-metric`, `add-decision`, etc.).

### New (2.0)

Directory-based memory following Memory Tool patterns:

```
.ariadna_planning/
├── memory/
│   ├── progress.md          # Current position, phase/plan status
│   ├── decisions.md         # Accumulated architectural decisions
│   ├── blockers.md          # Active blockers/concerns
│   ├── metrics.md           # Velocity, per-phase performance
│   ├── session.md           # Last session context, resume point
│   └── history.md           # Computed from SUMMARY.md frontmatter
├── PROJECT.md               # Vision, constraints (unchanged)
├── ROADMAP.md               # Phase breakdown (unchanged)
├── REQUIREMENTS.md          # Requirements (unchanged)
├── config.json              # Configuration (unchanged)
└── phases/                  # Phase directories (unchanged)
```

### Tool Interface

`ariadna-tools state` adopts Memory Tool verbs:

| Command | Maps to Memory Tool | Purpose |
|---------|-------------------|---------|
| `state view <path>` | `view` | Read a memory file or list directory |
| `state create <path> <content>` | `create` | Create a new memory file |
| `state update <path> <old> <new>` | `str_replace` | Replace text in a memory file |
| `state insert <path> <line> <text>` | `insert` | Insert text at a specific line |
| `state delete <path>` | `delete` | Remove a memory file |
| `state list` | `view` (directory) | View the memory directory |

### Design Principles

- **Granular files over monolith** — Each concern gets its own file. An agent needing decisions doesn't load metrics.
- **History digest persisted** — The SUMMARY.md frontmatter scan writes to `memory/history.md` instead of computing on-the-fly.
- **Session continuity unified** — `session.md` replaces both STATE.md's "Session Continuity" section and the `continue-here.md` template.
- **Init returns paths** — Agents read memory files they need rather than Init pre-loading everything.

## Agent Redesign

### New Agent Format

Agents are ~50-80 lines describing what to achieve:

```markdown
---
name: ariadna-executor
description: Executes a plan by implementing tasks with atomic commits
tools: [Read, Write, Edit, Bash, Grep, Glob]
---

<role>
You are a Rails developer executing a specific plan. You implement
tasks, make atomic commits per task, and produce a summary.
</role>

<goal>
Implement all tasks in the provided PLAN.md. Each task gets its own
commit. Produce SUMMARY.md with what was built, key files, and
dependencies on completion.
</goal>

<boundaries>
- Auto-fix bugs, missing imports, and blocking issues without asking
- Ask before making architectural changes not in the plan
- Never modify files outside the plan's scope without justification
- Follow Rails conventions from loaded Skills
</boundaries>

<output>
Return a SUMMARY.md with frontmatter:
- provides: what this plan delivers
- affects: which phases depend on this
- tech_stack: gems/libraries added
- files_modified: count
- tasks_completed: count
</output>
```

### What Gets Removed from Agents

- Step-by-step execution flows (trust 4.6 to figure out how)
- Priority numbering on steps
- Explicit parallelism instructions (4.6 parallelizes natively)
- Verbose deviation rules (collapsed to 2 boundary lines)
- "CRITICAL/MUST/NEVER" language (4.6 overtriggers on this)

### What Stays

- Role identity (focuses behavior)
- Output format specification (structured results matter)
- Boundaries (safety guardrails)
- Skills loading references (agents load Rails Skills as needed)

### Agent Consolidation: 14 → 6

| Keep | What Merged/Removed | Rationale |
|------|-------------------|-----------|
| `ariadna-executor` | Absorbs `backend-executor`, `frontend-executor`, `test-executor` | Domain routing happens via Skills, not separate agents |
| `ariadna-planner` | Absorbs `phase-researcher` inline research | 4.6 does inline research naturally |
| `ariadna-verifier` | Absorbs `integration-checker` cross-phase checks | Same verification capability |
| `ariadna-debugger` | Stays standalone | Distinct workflow with persistent state |
| `ariadna-roadmapper` | Absorbs `project-researcher`, `research-synthesizer` | 4.6 handles research + synthesis inline |
| `ariadna-codebase-mapper` | Stays standalone | Read-only analysis, distinct purpose |
| — | `ariadna-plan-checker` removed | Planner self-checks with adaptive thinking |

```
│   ├── JOBS.md               # ActiveJob patterns, error handling
│   └── API.md                # API design, serialization, versioning
├── rails-frontend/
│   ├── SKILL.md              # Entry point: Hotwire, Turbo, Stimulus
│   ├── VIEWS.md              # View patterns, partials, helpers
│   ├── COMPONENTS.md         # ViewComponent/Phlex patterns
│   └── ASSETS.md             # Asset pipeline, importmaps
├── rails-testing/
│   ├── SKILL.md              # Entry point: Minitest strategy, structure
│   ├── FIXTURES.md           # Fixture patterns, factories

└── rails-performance/
    ├── SKILL.md              # N+1, caching, DB tuning
    └── PROFILING.md          # Benchmarking, profiler usage
```

### SKILL.md Format

```yaml
---
name: rails-backend
description: Ruby on Rails backend conventions — models, controllers,
  jobs, API design. Use when implementing Rails backend code, creating
  models, writing controllers, or designing APIs.
---

# Rails Backend Conventions

Vanilla Rails with minimal dependencies. Follow the Rails Way.

## Architecture
- MVC with thin controllers, rich models
- RESTful routes, resource-oriented design
- Concerns for shared behavior, not inheritance hierarchies

For detailed model patterns, see [MODELS.md](MODELS.md).
For controller conventions, see [CONTROLLERS.md](CONTROLLERS.md).
```

### Progressive Disclosure

| Level | When Loaded | Token Cost | Content |
|-------|------------|------------|---------|
| Level 1: Metadata | Always (at startup) | ~100 tokens per Skill | `name` and `description` from frontmatter |
| Level 2: Instructions | When executor works on matching domain | <5k tokens | SKILL.md body |
| Level 3: Resources | As needed during implementation | Varies | MODELS.md, CONTROLLERS.md, etc. |

### Executor-Skill Integration

The single `ariadna-executor` loads the relevant Skill based on the plan's `domain` frontmatter field:

- `domain: backend` → loads `rails-backend` Skill
- `domain: frontend` → loads `rails-frontend` Skill
- `domain: testing` → loads `rails-testing` Skill
- Security and performance Skills loaded during verification

### Standalone Usage

Skills are usable independently of Ariadna's orchestration. A developer who doesn't use plan/execute/verify can still install Rails Skills for general development assistance.

## Workflow & Command Simplification

### New Workflow Format

Workflows become concise goal documents (~30 lines vs current ~200+ lines):

```markdown
---
name: execute-phase
description: Execute all plans in a phase with parallel agents
---

<goal>
Execute all incomplete plans in phase {N}. Each plan is handled by
an ariadna-executor agent. Plans sharing a wave number run in parallel.
Higher waves wait for lower waves to complete.
</goal>

<context_loading>
Run: ariadna-tools init execute-phase {N}
Returns JSON with: phase_dir, plans, incomplete_plans,
execution config, and memory file paths.
</context_loading>

<constraints>
- Spawn one executor agent per plan
- Pass the full PLAN.md content to each executor
- Load relevant Rails Skills based on plan domain field
- After each wave, read SUMMARY.md files to verify completion
- Update memory/progress.md after each wave
</constraints>

<success_criteria>
- All plans have SUMMARY.md files
- memory/progress.md reflects completion
- No executor reported unresolved blockers
</success_criteria>

<on_completion>
If verifier is enabled in config, suggest running verify-work.
</on_completion>
```

## Init Tool & Ruby Code Changes

### Init Tool

**Before (1.x):** 620 lines. Per-workflow methods. Returns full file contents via `--include` flags.

**After (2.0):** ~200 lines. Returns paths and metadata. Agents read what they need.

```ruby
# 2.0: Returns paths and metadata, not contents
{
  phase_dir: "/path/to/phases/01-foundation",
  plans: [{name: "01-01-PLAN.md", path: "...", domain: "backend", wave: 1}],
  memory_dir: ".ariadna_planning/memory/",
  config: {model_profile: "balanced", verifier: true},
  skills: ["rails-backend", "rails-frontend"]
}
```

### Ruby Module Changes

| Module | Change |
|--------|--------|
| `StateManager` (498 lines) | Rewrite for Memory Tool patterns. Operates on `memory/` directory. New verb-based interface (view/create/str_replace/delete). Retains convenience methods (`record-metric`, `add-decision`) as wrappers around raw str_replace operations. |
| `Init` (620 lines) | Shrink to ~200 lines. Returns paths, metadata, and config — not file contents. Per-workflow methods remain but are thin: they resolve phase info, list plans with wave/domain metadata, and point agents to `memory/` paths. Agents decide which files to read based on their goal. |
| `Verification` (606 lines) | Simplify significantly. Plan-structure verification and artifact checks move into the verifier agent's goal (4.6 handles this natively). Keep commit verification and phase-completeness checks as tool subcommands that the verifier agent can call. Target ~200 lines. |
| `PhaseManager` (356 lines) | Simplify — remove methods that duplicate 4.6's native capabilities |
| `RoadmapAnalyzer` (262 lines) | Keep — structured ROADMAP.md parsing is valuable |
| `ConfigManager` (234 lines) | Simplify — fewer config options with reduced agent count |
| `Installer` (267 lines) | Update to install Skills to `.claude/skills/`, commands to `commands/`, agents to `agents/`. Skills follow same SHA256 manifest pattern. Skills install to `~/.claude/skills/` (global) or `.claude/skills/` (local), matching the current global/local pattern. |
| `ModelProfiles` (95 lines) | Update agent list (14 → 6), keep generic `opus`/`sonnet`/`haiku` identifiers |
| `Frontmatter` (266 lines) | Update parsing for SKILL.md format alongside existing agent/workflow frontmatter |
| `TemplateFiller` (119 lines) | Fewer templates (~12 vs 34), same pattern |
| `CLI` (136 lines) | Update subcommand routing for simplified tool interface |
| `Output` (60 lines) | Keep as-is — JSON/error output utilities |
| `GitIntegration` (107 lines) | Keep as-is — commit formatting and verification |
| `Utilities` (63 lines) | Keep as-is — shared helpers |

### Template Consolidation: 34 → ~12

**Keep (12):** `project.md`, `roadmap.md`, `requirements.md`, `config.json`, `summary.md`, `verification-report.md`, `DEBUG.md`, `milestone-archive.md`, `milestone.md`, `UAT.md`, `discovery.md`, `research.md`

**Remove — top-level (10):** `state.md` (replaced by memory/), `continue-here.md` (merged into session.md), `planner-subagent-prompt.md` (agents self-contained), `phase-prompt.md` (planner loads context directly), `summary-minimal.md`, `summary-standard.md`, `summary-complex.md` (single template, 4.6 scales naturally), `user-setup.md`, `debug-subagent-prompt.md` (debugger self-contained), `context.md` (planner handles inline)

**Remove — codebase/ subdirectory (7):** `architecture.md`, `concerns.md`, `conventions.md`, `integrations.md`, `stack.md`, `structure.md`, `testing.md`. These codebase analysis templates are absorbed by the `ariadna-codebase-mapper` agent, which produces its own structured output. The mapper agent's output format is defined in its goal, not in external templates.

**Remove — research-project/ subdirectory (5):** `ARCHITECTURE.md`, `FEATURES.md`, `PITFALLS.md`, `STACK.md`, `SUMMARY.md`. Research output templates are absorbed by the `ariadna-roadmapper` agent, which handles research inline and structures its own output.

## Implementation Strategy: Vertical Slice

### Phase 1: Foundation

- Memory/State system (new StateManager + `memory/` directory)
- Init tool rewrite (paths not contents)
- Model profiles update (6 agents, generic model names)
- Config simplification

### Phase 2: Content

- 5 Rails Skills (extract from current guides + references)
- 3 lean agents (planner, executor, verifier)
- 3 lean workflows (plan-phase, execute-phase, verify-work)

### Phase 3: Wiring

- 3 commands updated to reference new workflows
- Installer updated for Skills directory
- End-to-end test: plan → execute → verify on a sample Rails app

### Phase 4: Rollout

- Apply patterns to remaining commands/workflows/agents
- Remove deprecated files
- Update README, CHANGELOG
- Release 2.0

### Validation Criteria

The vertical slice is validated when:

1. A user can run `/ariadna:plan-phase 1` and get a plan created by the lean planner with Rails Skills loaded
2. `/ariadna:execute-phase 1` spawns lean executors that use Skills for domain knowledge
3. `/ariadna:verify-work 1` validates goal achievement using goal-backward verification
4. State persists in `memory/` directory between commands
5. Total prompt data for the 3-command loop is <40% of the current 1.x size

## Size Targets

| Component | 1.x (actual) | 2.0 Target | Reduction |
|-----------|-------------|------------|-----------|
| Agents | 14 files, 8,170 lines | 6 files, ~400 lines | ~95% |
| Workflows | 30 files, 9,281 lines | 10 files, ~300 lines | ~97% |
| Commands | 27 files, 1,573 lines | 14 files, ~500 lines | ~68% |
| Templates | 34 files, 8,824 lines | 12 files, ~800 lines | ~91% |
| References | 14 files, 3,581 lines | 0 (absorbed by Skills + agents) | 100% |
| Skills | 0 | 5 Skills, ~15 files, ~3,000 lines | New |
| Ruby tools | 3,789 lines | ~2,200 lines | ~42% |
| **Total prompt data** | **119 files, 31,429 lines** | **42 files, ~5,000 lines** | **~84%** |

The overall prompt surface shrinks by ~84% (from ~31K to ~5K lines) while adding portable Rails Skills (~3,000 lines) that serve double duty as standalone resources.

Note: The Skills content is partially new. Approximately half migrates from existing guides and references (~1,600 lines of source material in domain executors and Rails references). The `rails-security` and `rails-performance` Skills are largely new content — the current codebase has minimal security and performance reference material.

## Risks and Mitigations

| Risk | Mitigation |
|------|-----------|
| Lean agents lose discipline (vibe coding) | Boundaries section explicitly prevents architectural drift. Verification step catches gaps. Test with real Rails projects. |
| 4.6 orchestration doesn't match hand-tuned workflows | Vertical slice validates before committing. Can add constraints to workflows if 4.6 needs more guidance in specific areas. |
| Memory directory becomes cluttered | Limit to 5-6 well-defined files. StateManager enforces structure. |
| Skills content requires significant new writing | ~1,600 lines migrate from existing content; ~1,400 lines are new (especially security/performance). Budget time for content authoring, not just migration. |
| Breaking existing projects | Clean break (2.0). Document migration path. Old STATE.md → memory/ migration tool. |
| 84% prompt reduction is aggressive | Vertical slice validates the target on the core loop first. If agents need more guidance, add constraints incrementally rather than reverting to verbose protocols. |

## Non-Goals

- Framework-agnostic orchestration (Rails-only by design)
- Claude.ai or API compatibility for orchestration (Claude Code-specific)
- Backward compatibility with 1.x STATE.md format
- Supporting pre-4.5 Claude models
- Migrating existing 1.x test suite — tests will be rewritten alongside module rewrites in Phase 1
